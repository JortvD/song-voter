# Playlist Voter

A collaborative song ranking game. Voters pick between two songs in duels; every
pick updates a shared score. Voters always see Your Ranking, while The Standings
stay hidden until the admin opens The Reveal.

**Current status: feature-complete.** Playlist Voter has invite-only accounts,
Spotify import with previews, duels, undo, Your Ranking, The Standings, The
Reveal, CSV export, an admin dashboard, rate limiting, backups and security
headers.

## Stack

- **Backend** — Rust, axum, sqlx, reqwest, tracing (plain-text structured logs)
- **Frontend** — React, TypeScript, Vite, Tailwind CSS
- **Database** — PostgreSQL 16
- **Packaging** — Docker Compose; the backend container serves the static frontend
- **TLS** — terminated by the host nginx (`vote.jortvd.nl` → `127.0.0.1:8765`)

## Quick start (Docker)

```bash
cp .env.example .env
# Set POSTGRES_PASSWORD, JWT_SECRET (openssl rand -hex 32),
# ADMIN_USERNAME, ADMIN_PASSWORD, and the Spotify settings below.
docker compose up -d --build
```

For playlist import, set `SPOTIFY_CLIENT_ID`, `SPOTIFY_CLIENT_SECRET` and
`SPOTIFY_REDIRECT_URI`, add the same redirect URI to the Spotify app dashboard,
then click **Connect** in the admin Playlist panel. Development Mode requires the
app owner to have Spotify Premium.

Then open <http://localhost:8765>. Sign in with the configured admin account,
create an invite code in the "Invites" panel, and register a voter account.

- `GET /healthz` — liveness, version and uptime (no DB access)
- `GET /readyz` — readiness, verifies PostgreSQL with `SELECT 1`

Logs are plain text on stdout, including a request id per request:

```bash
docker compose logs -f backend
```

## Auth & invites

- Registration is **invite-only**. Codes are 10 uppercase hex characters, single
  use, and generated by an admin.
- Passwords are hashed with Argon2; sessions are JWTs in an `HttpOnly`,
  `SameSite=Lax` cookie (`pv_session`, 7 days by default).
- The admin account is bootstrapped from `ADMIN_USERNAME` / `ADMIN_PASSWORD` on
  startup, so the first login never needs an invite. If the username already
  exists it is promoted to admin; the password is never overwritten.
- Every login, failed login, registration, logout and invite creation is written
  to the `auth_events` audit table and to the logs.

## Playlist import

- _Add_ `SPOTIFY_CLIENT_ID`, `SPOTIFY_CLIENT_SECRET` and
  `SPOTIFY_REDIRECT_URI` to `.env`. The redirect URI must exactly match the one
  registered in the Spotify app dashboard.
- Open the admin **Playlist** panel and click **Connect** to authorize the
  account that owns (or collaborates on) the playlist. The app stores the
  refresh token server-side and refreshes access tokens automatically.
- Since Spotify's **February 2026 API migration**, Development Mode apps can
  only read the items of playlists owned by, or collaborated on by, the
  authenticated user. Client credentials alone are no longer sufficient, even
  for public playlists. Development Mode also requires the app owner to have an
  active Spotify Premium subscription.
- Paste a playlist URL, a `spotify:playlist:…` URI, or a bare 22-character ID.
  Up to 2,000+ tracks are imported in pages of 50, with retry/backoff for
  Spotify rate limits and transient errors.
- Local files, podcast episodes, unavailable tracks and duplicate entries are
  skipped and counted in the import summary. Each track's 30-second Spotify
  preview URL is stored when available. When the Web API returns a null
  `preview_url` (common in Development Mode), the backend reads the preview MP3
  URL from the track's public Spotify embed page in the background.
- Importing a different playlist deactivates the previous one. Re-importing the
  same playlist refreshes metadata and upserts tracks — scores and pick counts
  are preserved. Tracks removed from Spotify are not deleted, so no history is
  lost.
- After deploying this version, existing tracks need their previews backfilled.
  Click **Fetch missing previews** in the Playlist panel, or re-import the
  playlist — both are safe and preserve picks.
- If no Spotify account is connected, the importer falls back to client
  credentials, which still works for Extended Quota apps reading public
  playlists.

### Playlist import returns 403

This is usually not a privacy problem anymore — it is Spotify's Development Mode
restriction. Check that you:

1. Added the exact redirect URI to the Spotify app, e.g.
   `https://vote.jortvd.nl/api/admin/spotify/callback`.
2. Set `SPOTIFY_REDIRECT_URI` in `.env` to that same value, then restarted the
   backend.
3. Clicked **Connect** in the Playlist panel and authorized with the account
   that owns or collaborates on the playlist.
4. Have an active Spotify Premium subscription on the app owner's account
   (required by Development Mode).

The connected account can read its own private playlists thanks to the
`playlist-read-private` scope, so the playlist no longer has to be public.

## Duel engine

`GET /api/matchup` returns two tracks plus progress (`compared_pairs`,
`total_tracks`). The duel engine works in three steps:

1. Take the 100 least-compared tracks (ties broken by least recently compared).
2. Among those, prefer the pair with the smallest score difference.
3. Exclude every pair this user has already been shown.

A pair is recorded in `seen_pairs` when it is served, so the same voter never sees
it twice — even if they abandon the duel. UUID ordering is normalised in the
table (`track_low < track_high`), while the left/right presentation is randomised
so position reveals nothing. When a small playlist runs out of unseen pairs, the
endpoint returns `409` with a friendly message.

The response exposes a public track shape only — no score, win or comparison
counts — so The Standings cannot be inferred from duels.

## Picking & scoring

`POST /api/vote` accepts `{ "track_a": "...", "track_b": "...", "winner": "..." }`.
A pick is only accepted for a duel that was served to that voter in the active
playlist, and only once per duel.

- Both tracks start at **1000**.
- `K = max(16, 40 − min(comparisons_a, comparisons_b) / 2)` — early picks move
  the standings, later picks settle them.
- Deltas are zero-sum: `delta_high = -delta_low`.
- Winner and loser ratings, `comparisons` and `wins` are updated in one
  transaction with both track rows locked in UUID order to avoid races.
- Every pick row stores the score before, the deltas, K, and comparison counts,
  forming the pick audit trail.
- The response does **not** expose ratings or deltas.

`POST /api/vote/undo` reverses the voter's most recent pick in the active playlist.
It subtracts the stored deltas, decrements comparisons/wins and deletes the pick.
The pair is kept in `seen_pairs`, so the duel screen can show it again and the
voter can immediately re-pick. Because undo subtracts deltas rather than restoring
snapshots, other voters' picks on the same tracks remain intact.

## The Duel screen

- `/duel` shows two compact cards with album art, title, artists and a native
  **30-second Spotify preview player**, sized to fit a desktop viewport. Press
  `Space` to play and switch between the two songs (starting with track A), `1`
  or `2` to pick a side, and `Z` to undo. Each side resumes where it left off;
  a new duel resets both previews. The currently playing card is outlined and
  marked **Playing**; the shortcut legend is always visible above the duel.
- Spotify's embedded iframe shows a "Use the Spotify app" prompt that cannot be
  hidden from outside the iframe. The native preview player avoids it entirely;
  tracks without a preview show an **Open in Spotify** link instead.
- After each pick the next duel loads immediately, and the page shows how many
  duels you have seen, how many songs you have covered, and how many picks you
  have made this session.
- `Undo` reverses the last pick and restores that duel so it can be re-picked.
- `/your-ranking` replays only your picks to build Your Ranking. It lists songs
  you have actually compared, with wins, duels and your score. It is private to
  you; The Standings stay sealed until The Reveal.

## The Reveal & The Standings

- `/standings` is the **public standings page**; it needs no login. Until the
  admin opens The Reveal, the page shows a sealed state with the playlist name and
  pick count, but no standings data.
- The admin **The Reveal** panel opens or seals the standings. Picking continues
  after The Reveal, and the standings can be sealed again.
- The standings are ordered by score, then wins, then title. It supports
  server-side search (`q`) across titles, artists and albums, plus pagination.
- **Download CSV** in the admin panel exports `rank,title,artists,album,spotify_id,rating,comparisons,wins`
  for every track, correctly quoting commas, quotes and newlines.
- `/your-ranking` is Your Ranking. `/standings` is the shared list.

## Admin dashboard

`/admin` is the control room, available to admin accounts:

- **Overview** — total picks, picks today, duels seen, active voters, registered
  accounts, songs compared and a 14-day picks-per-day graph.
- **System** — backend version, environment, uptime and Postgres readiness,
  visible only to the admin.
- **Voters** — every account with picks, duels seen, join date and last activity;
  server-side username search and pagination.
- **Standings** — all tracks with score, duels and wins, even while The Standings
  are still sealed; search and pagination.
- **Operations** — playlist import, Spotify connection, The Reveal control, CSV
  export and invite management.
- **Danger zone** — reset all picks, duels and scores for the active playlist
  (and seal The Standings), or remove the playlist entirely to return to the
  empty state. Both require typed confirmation; voters, invites and the Spotify
  connection are kept.

## Security, operations & backups

- **Rate limiting** — login attempts are limited per client IP per minute and
  registrations per client IP per hour. Both are configurable with
  `AUTH_LOGIN_RATE_LIMIT` / `AUTH_REGISTER_RATE_LIMIT`.
- **Security headers** — responses include a strict CSP, `X-Frame-Options:
  DENY`, `X-Content-Type-Options: nosniff`, a referrer policy and a permissions
  policy. API responses are marked `Cache-Control: no-store`.
- **Sessions** — JWT in an HttpOnly, SameSite=Lax cookie; Secure in production.
  Expired/revoked sessions are detected by the frontend and drop you back to the
  sign-in screen.
- **Request timeout** — HTTP requests are capped at 60 seconds.
- **Backups** — run `./scripts/backup.sh` (writes `backups/playlist-voter-*.sql.gz`,
  keeps 14 days). Schedule it with cron, for example:
  ```
  15 3 * * * cd /srv/playlist-voter && ./scripts/backup.sh >> backups/cron.log 2>&1
  ```
  Restore with `./scripts/restore.sh backups/<file>.sql.gz`. Backups contain
  password hashes and Spotify tokens — keep them private.
- **Nginx** — use `deploy/nginx/vote.jortvd.nl.conf`. It listens on HTTP port
  80 and proxies to the compose host port 8765; run `certbot --nginx` afterwards
  and it will add HTTPS + the redirect. Proxy all paths so SPA routes work:
  ```nginx
  location / {
      proxy_pass http://127.0.0.1:8765;
      proxy_set_header Host $host;
      proxy_set_header X-Real-IP $remote_addr;
      proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
      proxy_set_header X-Forwarded-Proto $scheme;
      proxy_read_timeout 75s;
  }
  ```
  `X-Forwarded-For` is used for audit logging and rate limiting; keep it set.

## Local development

Backend (needs a reachable PostgreSQL; `docker compose up -d db` starts one):

```bash
cd backend
export DATABASE_URL=postgres://ulltop2000:change-me@localhost:5432/ulltop2000
export JWT_SECRET=$(openssl rand -hex 32)
export ADMIN_USERNAME=admin ADMIN_PASSWORD=change-me
export COOKIE_SECURE=false   # plain HTTP on localhost

```

To reach the compose database from the host, temporarily publish its port in
`compose.yaml` (`ports: ["127.0.0.1:5432:5432"]`), or run the backend inside
compose as well.

Frontend:

```bash
cd frontend
npm install
npm run dev        # http://localhost:5173, proxies /api, /healthz, /readyz to :8080
```
